# Архитектура: предложения

Принято направление: Python для ядра/backend, отдельный веб-интерфейс, локальное развёртывание. Ниже — предлагаемые границы, не выбранные зависимости или версии.

## Ядро

Обычная независимая библиотека: мир, сетка и реестр сущностей, правила, RNG, шаг симуляции, VM, ресурсы, наследование и минимальные метрики. Без импортов HTTP, WebSocket, UI и часов для игровых решений. Источник истины — состояние мира; сетка и реестр должны согласовываться. Ошибка операции не должна оставлять частичное изменение.

В задаче 001 только мир, ID, границы, RNG и каркас шага. Обработчики для тестов демонстрируют планирование без реализации организмов. В 002 добавляется независимая управляющая VM в `core/vm.py`: сенсоры, исполнитель и RNG передаются явно; привязки к World/Entity нет. В 003 `core/biology.py` владеет приватным World, ресурсными снимками и резервом; `OrganismAdapter` соединяет его с независимой VM. World.step принимает необязательный явный порядок ID, сохраняя поведение по умолчанию. В 004 `World.run_tick` оборачивает весь биологический тик одной границей счётчика; World.step сохраняет техническое поведение. Списки останков/растений/организмов фиксируются заранее; shuffle каждой живой фазы выполняется непосредственно перед ней. Неизменяемые ResourceEntity хранят возраст и происхождение, RulesConfig/PlantRules — параметры. Смерть переводит запасы в новый ID останков без ресурсного удаления. VM после действия вызывает необязательный is_active, возвращая adapter_stopped при смерти, без зависимости от биологии. Счётчики событий и численности доступны как снимок metrics. Сериализация добавляется отдельно.

## Runtime

Принято в 007: `core/runtime.py` владеет одним приватным BiologicalWorld. Синхронные start/pause/step/advance/reset имеют явные состояния paused/running/failed и guard против вложенных команд. start меняет только состояние; внешний код вызывает advance. Новый мир готовится до замены; run_id генерируется UUID независимо от RNG мира. expected_run_id отвергает команды старого опыта до эффектов.

Снимки и детали — отделённые словари/списки со скалярными данными, без доступа к миру; поле не содержит геномов. Исключение тика сохраняет failed и сведения об ошибке. Снимки failed явно помечены незавершёнными; последняя успешная граница тика сохраняется отдельно, отката нет. Только reset восстанавливает работу. Чтение во время команды запрещено, многопоточный доступ не поддерживается.

Для будущего API предлагается один долгоживущий процесс, владеющий этим runtime. Граница — команды с ожидаемым run_id и ответы с состоянием/снимком/ошибкой; транспорт и очереди обсуждаются в следующей задаче. API не получает ссылку на мир. Ни процессы, ни протокол доставки пока не реализуются.

## API

Адаптер команд, DTO и ошибок; не место реализации биологических правил. Кандидаты: FastAPI, HTTP для команд и деталей, WebSocket для снимков. Версии и схемы выбираются в отдельной итерации. Предлагаются подтверждения применения команд, идентификаторы опыта/команды/ревизии, защита от повторов, полный снимок после reconnect и ограничение очереди снимков медленного клиента. Локальное подключение через loopback; облачный сервис не нужен.

## Интерфейс

Кандидаты: React, TypeScript, Vite, Canvas 2D. Интерфейс рисует последнее завершённое состояние, отправляет команды и инспектирует сущность по ID. Частоты расчёта, публикации и рисования независимы; геномы можно получать отдельно для инспектора. Полные компактные снимки — стартовый кандидат; delta-протокол после измерений.

## Хранение и инструменты

Кандидат — версионированные JSON-снимки без обязательной БД. Для продолжения нужны состояние RNG, счётчики tick/ID, конфигурация и все игровые данные; одного seed недостаточно. Проверять загрузку полностью до замены мира.

Для итераций 001–004 приняты стандартная библиотека Python и `unittest`. Используется доступный Python 3.13.0 без установки новой версии или пакетов. Ядро находится в `core/`, проверки — в `tests/`. Будущие зависимости и версии выбираются отдельно. Numba/Rust и иные оптимизации обсуждать после профилирования.

Направление зависимости: интерфейс → API → runtime → ядро. Headless-клиент вызывает то же ядро без API. Нормативные механики — [rules.md](rules.md); последовательность разработки — [roadmap.md](roadmap.md).

## Принято в 006: отчёт эксперимента

`core/scenarios.py` хранит неизменяемые явные исходные сценарии. `core/experiment.py` собирает мир, запускает ограниченный расчёт, проверяет инварианты каждый тик и отдельно записывает историю/JSON. Отчёт не содержит данных для продолжения мира. Все наблюдения читают снимки без RNG.

BiologicalWorld с явным флагом record_deaths фиксирует неизменяемые DeathRecord в точке смерти до замены ID. Контекст задаётся вызывающей фазой/действием. CLI не выводит причины по останкам и не меняет параметры по умолчанию. Формат и версия правил в отчёте явные; время запуска не используется в игровых данных.
