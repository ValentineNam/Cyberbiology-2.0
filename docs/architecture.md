# Архитектура: предложения

Принято направление: Python для ядра/backend, отдельный веб-интерфейс, локальное развёртывание. Ниже — предлагаемые границы, не выбранные зависимости или версии.

## Ядро

Обычная независимая библиотека: мир, сетка и реестр сущностей, правила, RNG, шаг симуляции, впоследствии VM, ресурсы, наследование и метрики. Без импортов HTTP, WebSocket, UI и часов для игровых решений. Источник истины — состояние мира; сетка и реестр должны согласовываться. Ошибка операции не должна оставлять частичное изменение.

В задаче 001 только мир, ID, границы, RNG и каркас шага. Обработчики для тестов демонстрируют планирование без реализации организмов. В 002 добавляется независимая управляющая VM в `core/vm.py`: сенсоры, исполнитель и RNG передаются явно; привязки к World/Entity нет. В 003 `core/biology.py` владеет приватным World, ресурсными снимками и резервом; `OrganismAdapter` соединяет его с неизменённой VM. World.step принимает необязательный явный порядок ID, сохраняя поведение по умолчанию. Сериализация добавляется отдельно.

## Runtime

Предлагается один владелец изменяемого мира. Сначала синхронный вызов `step`; затем управление паузой, шагами и запуском. Команды применять между тиками, публиковать только законченные состояния. Для API рассмотреть долгоживущий отдельный процесс расчёта с ограниченной очередью; необходимость подтвердить измерениями. Несколько серверных workers не должны независимо владеть одним опытом.

## API

Адаптер команд, DTO и ошибок; не место реализации биологических правил. Кандидаты: FastAPI, HTTP для команд и деталей, WebSocket для снимков. Версии и схемы выбираются в отдельной итерации. Предлагаются подтверждения применения команд, идентификаторы опыта/команды/ревизии, защита от повторов, полный снимок после reconnect и ограничение очереди снимков медленного клиента. Локальное подключение через loopback; облачный сервис не нужен.

## Интерфейс

Кандидаты: React, TypeScript, Vite, Canvas 2D. Интерфейс рисует последнее завершённое состояние, отправляет команды и инспектирует сущность по ID. Частоты расчёта, публикации и рисования независимы; геномы можно получать отдельно для инспектора. Полные компактные снимки — стартовый кандидат; delta-протокол после измерений.

## Хранение и инструменты

Кандидат — версионированные JSON-снимки без обязательной БД. Для продолжения нужны состояние RNG, счётчики tick/ID, конфигурация и все игровые данные; одного seed недостаточно. Проверять загрузку полностью до замены мира.

Для итераций 001–003 приняты стандартная библиотека Python и `unittest`. Используется доступный Python 3.13.0 без установки новой версии или пакетов. Ядро находится в `core/`, проверки — в `tests/`. Будущие зависимости и версии выбираются отдельно. Numba/Rust и иные оптимизации обсуждать после профилирования.

Направление зависимости: интерфейс → API → runtime → ядро. Headless-клиент вызывает то же ядро без API. Нормативные механики — [rules.md](rules.md); последовательность разработки — [roadmap.md](roadmap.md).
